# Lane: Lane 8 — Security & Privacy

## Executive summary
A sellable multi-branch blood bank system handles special-category health data (donors + recipients) and GxP-regulated release decisions, so it must clear the strictest common denominator across GDPR (privacy), 21 CFR Part 11 (electronic records/signatures), AABB Standards + EU GMP Annex 11 (computerized systems), and ISO 27001/HIPAA-grade controls. This requires: (a) fine-grained permission-based RBAC with enforced segregation of duties so the person who performs/interprets testing cannot also release the unit, plus audited break-glass; (b) modern credential security — Argon2id/bcrypt hashing, mandatory MFA for release/admin roles, idle + absolute session timeouts, and lockout with throttling; (c) TLS 1.2+ in transit and encryption at rest via MySQL TDE for the tablespace PLUS application-level (envelope) field encryption for direct identifiers, with keys held in a KMS/HSM outside MySQL; (d) GDPR-grade privacy: documented lawful basis (donor consent is withdrawable; recipient processing rests on vital-interest/healthcare provision, NOT consent), data-subject-rights workflows, pseudonymization, and legally-mandated long retention that overrides erasure; (e) Part 11 electronic signatures (two distinct ID components, signature manifestation captured in the record, cryptographically bound to an append-only audit trail). Vanilla PHP/MySQL can implement most of this but CANNOT by itself provide tamper-evident immutability, real key isolation, or trustworthy time — those must be added with hash-chaining, a KMS, and an authoritative time source. Plainly: the stack is viable only if augmented; an unaugmented LAMP build will fail a Part 11 / Annex 11 audit and a GDPR DPIA.

## Standards referenced
- 21 CFR Part 11 — Electronic Records; Electronic Signatures (§11.10 controls, §11.50 signature manifestations, §11.70 signature/record linking, §11.100 general/certification, §11.200 signature components & controls, §11.300 identification code/password controls)
- 21 CFR 606.160(d) — Blood establishment records, ≥10-year retention; 606.100/630 donor suitability & test verification
- EU Directive 2002/98/EC (Blood Directive) and Commission Directive 2005/61/EC — traceability donor↔recipient, ≥30-year data retention
- EU GMP Annex 11 — Computerised Systems (validation, audit trail, access control, data integrity)
- GDPR (Regulation 2016/679) — Art 5, 6, 9 (special-category health data), 15-20 (data-subject rights), 17 (erasure & limits), 25 (data protection by design), 32 (security of processing), 33/34 (breach notification), 35 (DPIA)
- AABB Standards for Blood Banks and Transfusion Services — independent verification, qualified second review before product release
- ISBT 128 — unique donation/component identification (supports traceability/pseudonym keys)
- HL7 / FHIR — interoperability and AuditEvent / Provenance resources for audit and signature exchange
- ISO/IEC 27001 (esp. A.5-A.18: access control, cryptography A.10, key management) and ISO 27799 (health informatics security)
- NIST SP 800-63B — authenticator/password guidance (no forced rotation, MFA)
- OWASP ASVS and Password Storage Cheat Sheet — Argon2id parameters, session, lockout
- RFC 6238 (TOTP), RFC 3161 (trusted timestamping), WebAuthn/FIDO2 (phishing-resistant MFA), TLS 1.2/1.3
- HIPAA Security Rule (45 CFR 164) — comparable access-control/audit/encryption controls for US hospital buyers

## Recommendations
- **[must-have] Permission-based RBAC, not role strings** — Replace any single role VARCHAR with a normalized model: users — roles (m:n via user_roles) — role_permissions — permissions, where permissions are fine-grained verbs on objects (e.g. donation.screen, test.perform, test.interpret, unit.label, unit.quarantine_release, unit.issue, request.approve, transfer.authorize, donor.read_pii, audit.read, user.manage, config.compatibility_rules.edit). Enforce server-side on EVERY endpoint via a central authorize($permission, $context) gate — never rely on hiding UI. Scope every permission to a branch_id so a tech at branch A cannot act on branch B; multi-branch users get explicit grants. Cache permissions per session but re-check on each mutating call.
- **[must-have] Enforced Segregation of Duties (SoD) for unit release** — Model SoD as data, not policy docs. The donation→release pipeline must require distinct user IDs at each gate: collector ≠ tester; for critical infectious-marker results require a second independent verification (test.perform vs test.interpret held by different people); the person who performed/interpreted screening MUST NOT hold unit.quarantine_release for that same unit. Enforce with a server-side check: on release, reject if released_by IN (collected_by, tested_by, interpreted_by) for that unit. Maintain a static SoD conflict matrix table (conflicting_permission_pairs) and block role assignments that violate it. AABB Standards require a qualified second review before product release; 21 CFR 606.100/630 require independent verification of donor suitability and test results.
- **[must-have] Break-glass emergency access with mandatory logging** — Provide a break_glass workflow: an authorized user can elevate to read otherwise-restricted PII or release in a life-threatening emergency by entering a reason code + free-text justification; the system grants a TIME-BOXED elevated session (e.g. 30 min), writes a high-severity immutable audit event BEFORE granting, raises a real-time alert to a supervisor/DPO, and flags the session for mandatory post-hoc review. Break-glass must never bypass logging or signature capture — it bypasses only the pre-authorization, not accountability. Required to satisfy emergency-issue clinical reality without weakening the default least-privilege posture.
- **[must-have] Password hashing: Argon2id (preferred) or bcrypt** — Use PHP password_hash() with PASSWORD_ARGON2ID (memory_cost >= 19 MiB, time_cost >= 2, parallelism 1 per OWASP) or PASSWORD_BCRYPT cost >= 12 as fallback. Never MD5/SHA without salt. Store only the hash; use password_verify() and password_needs_rehash() to upgrade transparently. Enforce a password policy (length >= 12, breach-list check) and rotation only on suspected compromise (NIST 800-63B discourages forced periodic rotation).
- **[must-have] Multi-factor authentication** — Mandate MFA (TOTP RFC 6238 via authenticator app, or WebAuthn/FIDO2 for phishing resistance) for all privileged roles: release, admin, DPO, config editors, and any break-glass elevation. TOTP is implementable in pure PHP (e.g. HOTP/TOTP libs) with secrets stored field-encrypted. WebAuthn is preferable for the sellable bar but needs the browser API + a relying-party verification step in PHP. Provide recovery codes (hashed). 21 CFR 11.10(d)/11.300 and GDPR Art 32 expect strong authentication for sensitive-data access.
- **[must-have] Session management: idle + absolute timeout, secure cookies** — Idle timeout 15 min for clinical/release roles; absolute session lifetime cap (e.g. 8–12 h) regardless of activity. Regenerate session ID on login and on privilege change (prevent fixation). Cookies: HttpOnly, Secure, SameSite=Strict, short-lived. Store sessions server-side (DB or Redis), not in client. Bind session to a re-authentication step before signing (Part 11 11.200 requires the signing component be re-entered for non-continuous sessions).
- **[must-have] Account lockout and brute-force throttling** — Progressive throttling + temporary lockout after N failed attempts (e.g. 5), with exponential backoff and per-account + per-IP rate limiting; log all failures to the audit trail; alert on repeated lockouts. Protect MFA endpoints equally. Avoid permanent lockout (DoS risk) — use time-boxed locks plus admin unlock. 21 CFR 11.300(d) requires detecting and reporting unauthorized attempts.
- **[must-have] Encryption in transit** — TLS 1.2+ (prefer 1.3) for all browser-server and server-server (inter-branch sync) traffic; HSTS; disable legacy ciphers. Enable TLS on the MySQL client connection (REQUIRE SSL on DB accounts) so app-DB traffic is encrypted, especially for multi-branch/remote DB topologies. mTLS for the inter-branch sync channel.
- **[must-have] Encryption at rest: TDE + application-level field encryption** — Two layers. (1) MySQL TDE (InnoDB tablespace encryption, available in MySQL 8 Enterprise and MariaDB; AES) protects whole files at rest against disk/backup theft but does NOT protect against an attacker with DB query access. (2) Application-level (envelope) encryption of direct identifiers and the most sensitive fields (donor/recipient name, national ID, contact, infectious-disease results) using AES-256-GCM via PHP openssl/libsodium, with a per-record data key wrapped by a master key in a KMS. This keeps plaintext out of SELECT results, logs, and replicas. Trade-off: encrypted fields cannot be indexed/searched directly — use blind indexes (HMAC of normalized value) for exact-match lookup, accept loss of range/LIKE queries.
- **[must-have] Key management outside MySQL** — Do NOT store encryption keys in PHP source, config files in webroot, or the same DB. Use a KMS/HSM (e.g. HashiCorp Vault, cloud KMS, or PKCS#11 HSM) or at minimum an OS keyring with envelope encryption: KMS holds the master key, app fetches/wraps data keys at runtime, keys are rotatable without re-encrypting all data (re-wrap data keys only). MySQL TDE keyring must also use a real keyring plugin, not file-based keyring on the same host for the sellable bar. Document key rotation, escrow, and access in a key-management SOP (ISO 27001 A.10 / Annex 11).
- **[must-have] GDPR lawful basis & consent capture (distinguish donor vs recipient)** — Capture and version the lawful basis per processing purpose. DONOR: explicit consent for donation + health screening (Art 9(2)(a)), withdrawable — but withdrawal cannot delete safety/traceability records mandated by law. RECIPIENT/PATIENT: do NOT rely on consent; rely on Art 9(2)(h) (provision of health care) and/or 9(2)(c) (vital interests) — patients in transfusion emergencies cannot consent. Store consent_records (subject_id, purpose, basis, version, timestamp, captured_by, withdrawal_ts) immutably. Surface a privacy notice and record its version shown.
- **[must-have] Data-subject rights workflows** — Implement endpoints/processes for access (Art 15 export of a subject's data), rectification (Art 16, as a corrective versioned record never a destructive overwrite of GxP data), erasure (Art 17 — MUST be refusable where retention is legally required for blood safety/traceability; implement as restriction/blocking + crypto-shredding of non-mandatory PII instead of deletion), restriction (Art 18), and portability (Art 20, machine-readable export). Every DSR action is itself an audited event. Provide a DPO dashboard.
- **[must-have] Retention periods (research-backed, long and legally binding)** — Blood records have statutory minimums that OVERRIDE erasure requests. EU Directive 2002/98/EC + Commission Directive 2005/61/EC require traceability data linking donor↔donation↔component↔recipient be kept at least 30 YEARS. US FDA 21 CFR 606.160(d) requires blood establishment records be kept at least 10 years (with some records — e.g. donor deferral/look-back — kept indefinitely/for the longer of 10 years or until product disposition + further). AABB aligns with these. Implement a retention_policy table keyed by record_class with min_retention_years and a legal_hold flag; the purge job must NEVER delete records under retention or legal hold. Default to the strictest applicable (30y for traceability) so it ports across regions.
- **[should-have] Pseudonymization & data minimization** — Separate direct identifiers into a restricted identity table referenced by a surrogate subject key; operational/analytical tables and reports use the pseudonym, not name/ID. Re-identification requires a separately-permissioned join (donor.read_pii). Pseudonymize data sent to non-clinical reporting/analytics and to lower environments (never copy production PII to dev/test — use synthetic or masked data). Satisfies GDPR Art 25 (data protection by design) and Art 32.
- **[must-have] 21 CFR Part 11 electronic signatures** — Each signing event must: use a signature composed of two distinct components — typically user ID (already authenticated) + a private password/PIN re-entered at signing (11.200(a)(1)); for a continuous session the first signing uses both components and subsequent ones at least one, with session controls (11.200(a)(1)(i-ii)). The signed record must DISPLAY the signature manifestation (11.50): printed/displayed name of signer, date & time of signing (from an authoritative/trusted clock, not client-supplied), and the MEANING of the signature (e.g. 'reviewed', 'approved for release', 'verified result'). Signatures must be linked to their records so they cannot be cut/copied/transferred (11.70). Signatures are equivalent to handwritten (11.3). Maintain the certification to FDA that e-signatures are legally binding (11.100(c)) as an organizational artifact.
- **[must-have] Immutable, tamper-evident audit trail bound to signatures** — Audit trail must be computer-generated, time-stamped, capture old+new values, who/when/why, and be non-modifiable by users (11.10(e), Annex 11 §9). Make it tamper-EVIDENT in MySQL via hash-chaining: each audit row stores hash = H(prev_hash || row_payload), creating a blockchain-style chain that detects insertion/deletion/edit. Periodically sign/anchor the chain head (e.g. nightly digest signed by a server key or sent to a WORM store / external timestamping authority RFC 3161). Electronic signatures store the audit_event hash they sign over, binding signature→record→chain. Use append-only DB privileges (app account has INSERT only on audit_log, no UPDATE/DELETE) and DB triggers that reject UPDATE/DELETE.
- **[should-have] Trusted time source** — Client clocks are untrustworthy for Part 11/Annex 11. Derive all signing and audit timestamps server-side from an NTP-synced server clock; for the highest bar, RFC 3161 timestamp tokens from a TSA for signature events. Record timezone in UTC. This is an explicit gap the PHP app must close — never accept a browser-supplied timestamp for a signed/audited action.
- **[should-have] DPIA, breach notification, and SOPs as deliverables** — Ship the system with a Data Protection Impact Assessment template (Art 35, mandatory for large-scale special-category processing), a 72-hour breach-notification procedure (Art 33/34), validation/IQ-OQ-PQ documentation (Annex 11 §4, computerized system validation), and SOPs for access control, key management, backup/restore, and audit review. A sellable GxP system is the software PLUS this documentation; hospitals' auditors will ask for it.
- **[should-have] Secure inter-branch sync & offline queue** — The offline-sync queue and inter-branch transfer carry PII and must be encrypted at rest in the queue (field-level), transmitted over mTLS, signed for integrity, and idempotent with conflict resolution that never silently overwrites a signed release. Queued audit/signature events must preserve original server-trusted timestamps and re-chain correctly on the central node. Reconcile SoD across branches (a release signed offline must still satisfy distinct-signer rules on merge).

- audit_log(id, ts_server_utc, actor_user_id, action, object_type, object_id, old_value, new_value, reason, prev_hash, row_hash) — INSERT-only, hash-chained; trigger blocks UPDATE/DELETE
- audit_chain_anchors(id, chain_head_hash, anchored_at, tsa_token, server_signature) — periodic notarization of the chain
- Add REQUIRE SSL on MySQL app accounts; separate audit-writer DB account with INSERT-only grant on audit_log

## PHP/MySQL feasibility
Vanilla PHP/MySQL/AJAX can implement the MAJORITY of this bar and is a defensible foundation, but NOT unaugmented. What PHP/MySQL does well natively: Argon2id/bcrypt via password_hash(); AES-256-GCM field encryption via libsodium/openssl; TOTP MFA; server-side sessions with idle/absolute timeouts and lockout; permission-based RBAC and SoD enforced in application logic + relational tables; TLS via the web server and REQUIRE SSL DB accounts; hash-chained audit rows and INSERT-only DB grants with UPDATE/DELETE-blocking triggers; Part 11 signature components (re-enter password at signing) and manifestation rows. What the stack CANNOT do at the sellable bar and MUST add: (1) Real key isolation — keys cannot live in PHP config/DB; requires an external KMS/HSM (Vault, cloud KMS, or PKCS#11). (2) True immutability/non-repudiation of the audit trail — MySQL alone is tamper-evident at best; needs external anchoring (RFC 3161 TSA, WORM/append-only store, or signed nightly digests off-host) because root/DBA can rewrite a self-contained chain. (3) Trusted time — must come from NTP/TSA, not the app or client. (4) MySQL TDE for files at rest requires MySQL 8 Enterprise or MariaDB with a proper keyring plugin (a licensing/edition cost), not the default community file engine. (5) WebAuthn/FIDO2 (phishing-resistant MFA, the stronger bar) needs added relying-party verification code. (6) Searchable encryption is unsolved natively — blind indexes give exact match only. (7) The compliance posture also demands non-software deliverables (DPIA, CSV validation IQ/OQ/PQ, SOPs, Part 11 §11.100(c) certification) that ship WITH the product. Verdict: feasible as PHP/MySQL core + mandatory bolt-ons (KMS, external audit anchoring/WORM, trusted time, possibly MySQL Enterprise/MariaDB for TDE). An unaugmented LAMP build will fail a Part 11/Annex 11 audit and a GDPR Art 35 DPIA — say so to the buyer rather than designing to a happy path.

## Risks & tradeoffs
- Field-level encryption defeats SQL indexing/search: name and national ID become non-searchable except via blind indexes (exact-match only); range queries, LIKE, and sorting on encrypted PII are lost — design lookups around surrogate keys and blind indexes early.
- MySQL hash-chained audit gives tamper-EVIDENCE, not tamper-PREVENTION. A DBA/root with full DB+host access can recompute the whole chain. True immutability requires external anchoring (WORM storage, RFC 3161 TSA, or write to a separate append-only system) — pure MySQL cannot guarantee it alone.
- MySQL TDE protects only files at rest; anyone with query access still sees plaintext. It is necessary but insufficient — hence the app-level layer. Community MySQL TDE/keyring options are weaker than Enterprise; file-based keyring on the same host provides little real protection.
- Key management is the hardest part on a LAMP stack: doing it without a real KMS/HSM (keys in config/env) is a common but audit-failing shortcut. Selling into hospitals likely requires shipping or integrating a KMS, adding deployment complexity beyond vanilla PHP.
- GDPR erasure vs statutory retention will conflict: erasure requests for donors/recipients MUST often be refused for 10–30 years for blood-safety traceability. This must be documented and defensible, or the vendor risks GDPR complaints; implement as restriction/crypto-shred of non-mandatory fields, not deletion.
- Trusted time and trusted random/crypto are environmental dependencies (NTP, libsodium, OpenSSL, possibly TSA) that the deploying hospital's infra must provide; the app cannot self-certify time.
- Offline-sync + SoD interact badly: an offline release may pass local SoD but conflict on merge; without careful conflict resolution you can produce a unit released by a single identity across nodes, violating SoD.
- 21 CFR Part 11 / Annex 11 compliance is also organizational (validation IQ/OQ/PQ, SOPs, signed certifications) — software alone cannot make a customer compliant; the sellable bar includes documentation deliverables, not just code.
- Plain PHP session handling and CSRF/XSS hardening must be rigorous (output encoding, prepared statements, CSRF tokens, CSP) — a single injection flaw exposes all decrypted PII at the app tier where keys live, the highest-value target.
