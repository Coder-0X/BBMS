# Lane: LANE 4 — DATA MODEL & STATE MACHINES

## Executive summary
A sellable blood bank system must treat the recipient, not just the request, as a first-class persistent entity: a patient registry keyed by a stable patient identifier carrying a longitudinal, immutable blood-group and antibody/alloantibody history that follows the patient across visits and branches, because a historically-identified clinically-significant alloantibody (e.g. anti-K, anti-Jka) must drive antigen-negative selection for life even when the current type-and-screen is negative (AABB Standards; the antibody does not have to be currently demonstrable to be transfusion-relevant). Component lineage must model donation -> processing/manufacturing event -> child component units as a directed acyclic graph so that look-back and recall (ISBT 128 traceability; FDA 21 CFR 606.160/610.46-610.47; EU 2005/61/EC Art. 5-6) can trace every component, intermediate, and pooled product derived from a donation, plus every prior donation by a now-reactive donor, and quarantine them in one operation. Every blood_unit must move through a formal state machine with guarded transitions (you cannot issue a quarantined, expired, reserved-to-another, or failed-QC unit) enforced in the database, not merely in PHP. Audit must be append-only and tamper-evident via per-row hash-chaining plus electronic-signature linkage (21 CFR Part 11 §11.10/§11.50/§11.70, §11.200), so a DBA with table access cannot silently rewrite history without breaking the chain. Vanilla PHP/MySQL can express all of these as schema and triggers, but true tamper-evidence and Part-11 signatures require controls (append-only storage, signing keys, periodic external anchoring) that MySQL alone does not provide and that must be added explicitly.

## Standards referenced
- ISBT 128 (ICCBBA Standard ST-001) — Donation Identification Number, product description codes, component lineage/division identifiers
- AABB Standards for Blood Banks and Transfusion Services — second ABO/Rh determination, historical antibody records, antigen-negative selection for clinically significant antibodies, sample validity
- FDA 21 CFR Part 11 — electronic records and electronic signatures (§11.10 controls, §11.50 signature manifestations, §11.70 signature/record linking, §11.200 signature components & re-authentication)
- FDA 21 CFR 606.160 — records (traceability) for blood establishments
- FDA 21 CFR 610.46 / 610.47 — HIV and HCV look-back requirements
- FDA 21 CFR 606.171 — reporting of product deviations
- EU Directive 2002/98/EC — quality and safety standards for blood
- EU Commission Directive 2005/61/EC — traceability requirements and serious adverse reaction/event (haemovigilance) notification
- EU Commission Directive 2005/62/EC — quality system standards
- HL7 FHIR R4 — Patient (identifier, link/merge), Specimen, Observation, AllergyIntolerance, BiologicallyDerivedProduct, ServiceRequest
- WHO Guidelines/Aide-Memoire for blood traceability and haemovigilance

## Recommendations
- **[must-have] Replace free-text patient_name with a persistent patients registry keyed by a stable MPI identifier** — Create patients(patient_id PK, mpi_uid CHAR(36) UNIQUE /* org-wide master patient index */, given_name, family_name, sex, date_of_birth, national_id_hash, created_by FK users, created_at, merged_into_patient_id NULL FK patients /* for de-dup merges, never hard-delete */, record_status ENUM('active','merged','blocked')). blood_requests.patient_name TEXT is removed and replaced with blood_requests.patient_id FK patients. Identity must be resolvable across branches: add patient_identifiers(id PK, patient_id FK, system VARCHAR /* e.g. 'MRN:BranchA','national-id','passport' */, value, is_primary BOOL, UNIQUE(system,value)) so the same human under different branch MRNs collapses to one patient_id. Map to HL7 FHIR Patient (identifier[], link[] for merges). Rationale: blood-group and antibody history are worthless if they cannot be re-associated to the same person on the next visit; free-text names cause duplicate records and mis-selection.
- **[must-have] Add an immutable, longitudinal patient blood-group history (never a single mutable column)** — patient_blood_groups(id PK, patient_id FK, abo ENUM('A','B','AB','O'), rh_d ENUM('pos','neg','weak_d','unknown'), method VARCHAR /* gel,tube,analyzer */, determined_at, determined_by FK users, verified_by FK users NULL /* two-person rule for first determination */, branch_id FK, source ENUM('current_testing','historical','external'), sample_id FK samples, is_discrepant BOOL DEFAULT 0, supersedes_id FK self NULL). Append-only: a new typing inserts a row, never UPDATEs. AABB requires a second ABO/Rh determination (or a comparison to a historical record) before issuing non-O/non-D-compatible cellular components; the registry provides exactly this prior record. A trigger raises is_discrepant and blocks electronic crossmatch release when a new typing conflicts with any prior confirmed typing for that patient (ABO discrepancy is a patient-safety stop). Expose latest confirmed ABO/Rh as a VIEW, not a stored column, so history is the source of truth.
- **[must-have] Add a lifelong antibody/alloantibody history that drives antigen-negative unit selection** — patient_antibodies(id PK, patient_id FK, specificity VARCHAR /* ISBT-aligned: anti-K, anti-Jka, anti-D, anti-E, anti-Fya, anti-c... */, antigen_system VARCHAR /* Kell,Kidd,Duffy,Rh... */, clinical_significance ENUM('significant','insignificant','unknown'), status ENUM('identified','suspected','historical_only','ruled_out'), first_identified_at, first_identified_branch FK, identified_by FK users, last_demonstrated_at NULL, evanescent BOOL DEFAULT 1 /* may become undetectable but stays clinically relevant */, autocontrol_positive BOOL, panel_ref VARCHAR, notes_signed_blob_id FK esign). CRITICAL guard: unit selection for this patient must filter blood_units by antigen-negativity for every specificity where clinical_significance='significant' AND status IN('identified','historical_only'), EVEN IF the current screen is negative — this is the core reason the history must be persistent and cross-visit. Add patient_transfusion_requirements(id PK, patient_id FK, requirement ENUM('antigen_negative','irradiated','cmv_negative','washed','hbs_neg','phenotype_matched'), antigen_spec NULL, reason, active BOOL, set_by FK, set_at) for standing requirements (e.g. irradiated-for-life post-HSCT). Maps to FHIR AllergyIntolerance/Observation + a custom transfusion-requirement profile.
- **[must-have] Model component lineage as donation -> processing_event -> child units (a DAG), supporting splits and pools** — Keep donations as the apheresis/whole-blood collection. Add manufacturing/processing as first-class events: processing_events(id PK, event_type ENUM('whole_blood_separation','apheresis_collection','split','irradiation','leukoreduction','pooling','wash','aliquot','thaw','pathogen_reduction'), performed_at, performed_by FK, branch_id, sop_version VARCHAR, esign_id FK). Lineage edges: unit_lineage(id PK, processing_event_id FK, parent_unit_id NULL FK blood_units, parent_donation_id NULL FK donations, child_unit_id FK blood_units, relationship ENUM('derived_from','split_from','pooled_into','aliquot_of')). A whole-blood donation produces RBC + plasma + platelet child blood_units via one separation event (parent_donation_id set). A split produces two child units from one parent_unit_id. A pool has multiple parent edges into one child (records donor contributors for pooled-product look-back). blood_units gains: din CHAR(13) /* ISBT 128 Donation Identification Number: 5-char facility + 2-digit year + 6 serial, plus flag/keyboard chars */, isbt_product_code CHAR(8) /* ISBT 128 product description code */, division_id CHAR(2) /* split/aliquot suffix, e.g. A0,B0 */, component_class ENUM('RBC','FFP','PLT','CRYO','WB','GRAN'), parent_donation_id FK donations. Recursive CTE over unit_lineage yields the full ancestor/descendant set for recall.
- **[must-have] Implement a formal blood_unit state machine with DB-enforced guarded transitions** — States ENUM on blood_units.status: quarantined (default at creation, pre-testing) -> in_testing -> available | failed_qc | discarded. From available: reserved (soft hold for a patient) -> crossmatched -> issued -> transfused | returned_to_stock | wasted. Cross-cutting terminal/exception states: expired, recalled, quarantined_holdback (look-back), transferred_out (inter-branch), destroyed. Define unit_state_transitions(id PK, from_status, to_status, requires_role, guard_rule) as a lookup the application and a BEFORE UPDATE trigger both consult. Hard guards enforced by trigger, NOT just PHP: (a) any -> issued blocked unless status='crossmatched' or electronic-crossmatch-eligible; (b) -> issued blocked if expiry_datetime <= NOW(); (c) quarantined/quarantined_holdback/recalled/failed_qc -> issued is forbidden (no path exists); (d) reserved/crossmatched unit cannot be issued to a different patient_id than the reservation holder; (e) recalled is reachable from ANY non-terminal state and is itself terminal except -> destroyed. Every transition writes a unit_status_events row (append-only: id, unit_id, from_status, to_status, reason, actor FK users, esign_id, occurred_at) — current status is denormalized for query speed but the event log is authoritative. Reject illegal transitions with SIGNAL SQLSTATE in the trigger so a buggy or malicious PHP path still cannot issue an expired/quarantined unit.
- **[must-have] Make audit_logs append-only and tamper-evident via per-row hash chaining** — Redesign audit_logs(id BIGINT PK AUTO_INCREMENT, seq BIGINT /* monotonic per chain */, occurred_at_utc DATETIME(6), actor_user_id FK, action, entity_table, entity_id, before_json JSON NULL, after_json JSON NULL, branch_id, prev_hash CHAR(64), row_hash CHAR(64), esign_id FK NULL). row_hash = SHA-256(seq || occurred_at_utc || actor || action || entity || before_json || after_json || prev_hash). prev_hash links to the previous row's row_hash, forming a chain: altering or deleting any historical row breaks every subsequent hash and is detectable by a verifier that recomputes the chain. Compute the hash server-side in a single audit-writer code path (or a MySQL BEFORE INSERT trigger) so callers cannot supply their own hash. Revoke UPDATE and DELETE on audit_logs from all application and admin roles; grant INSERT only. Periodically (e.g. hourly) sign the current head row_hash and persist/anchor it externally (separate append-only store, WORM bucket, or notarization) so even root/DBA tampering that recomputes the whole chain is caught by divergence from the anchored head. This is the part vanilla MySQL cannot guarantee alone — see feasibility.
- **[must-have] Add electronic-signature records linked to safety-critical actions (21 CFR Part 11)** — electronic_signatures(id PK, signer_user_id FK, signed_at_utc DATETIME(6), meaning ENUM('reviewed','approved','released','verified','rejected','quarantine_release') /* 11.50 signature manifestations */, auth_method ENUM('password_reauth','mfa'), reauth_at /* 11.200 requires identity re-verification at signing */, signed_payload_hash CHAR(64) /* binds the signature to exact record content */, audit_log_id FK). Reference esign_id from quarantine release (in_testing->available), QC pass/fail, electronic crossmatch release, issue authorization, recall initiation, and patient blood-group first determination. Part 11 §11.70 requires the signature be cryptographically/linked to its record so it cannot be excised and reused; signed_payload_hash provides that binding. §11.200 requires that a signing not in a continuous session re-authenticate the user — enforce reauth at each signing event. Store the meaning explicitly so the printed/displayed record shows who did what and why (§11.50).
- **[must-have] Add a recall/look-back workflow object that drives mass quarantine and trace queries** — recalls(id PK, trigger ENUM('donor_seroconversion','positive_repeat_test','recipient_reaction','equipment_failure','recall_notice'), trigger_donor_id NULL FK donors, trigger_donation_id NULL FK donations, marker VARCHAR /* HIV,HBV,HCV,HTLV,syphilis,bacterial */, opened_at, opened_by FK, esign_id, status ENUM('open','tracing','quarantined','dispositioned','closed','reported_to_authority')). recall_items(id PK, recall_id FK, blood_unit_id FK, role ENUM('implicated_component','co_component','recipient_traced'), disposition ENUM('quarantined','destroyed','already_transfused_recipient_notified','not_found'), recipient_patient_id NULL FK patients). On donor seroconversion: recursive CTE over donations->unit_lineage->blood_units for ALL prior donations by trigger_donor_id (look-back window per AABB/regulatory guidance, typically tracing back to a prior negative donation) -> bulk transition reachable in-stock units to quarantined_holdback/recalled, and for already-issued units join issue_transactions to surface recipient_patient_id for clinician notification (EU 2005/61/EC haemovigilance traceability; FDA 610.46-610.47 HCV/HIV look-back). This is the operational reason lineage and the patient registry must both exist and be linked.
- **[should-have] Link issue_transactions to patient_id, the specific crossmatch, and an issue electronic signature** — issue_transactions gains: patient_id FK patients (replacing any free-text), crossmatch_id FK crossmatches NULL (NULL only when electronic-crossmatch-eligible and recorded as such), issue_esign_id FK electronic_signatures, intended_branch FK, abo_check_passed BOOL. Add crossmatches(id PK, patient_id FK, blood_unit_id FK, method ENUM('serologic_ahg','immediate_spin','electronic'), result ENUM('compatible','incompatible','electronic_release'), antibody_screen_result, performed_at, performed_by FK, verified_by FK). A trigger blocks insert into issue_transactions if the patient has an active antigen-negative/irradiated/CMV requirement not satisfied by the chosen unit, or if abo_check_passed is false — enforcing the patient registry's safety data at the moment of issue.
- **[should-have] Add sample and test-result tables so typings/antibodies are traceable to a specimen and not orphaned** — samples(id PK, patient_id NULL FK, donor_id NULL FK, collected_at, collected_by FK, sample_type, expiry /* type-and-screen sample validity, e.g. 3 days if transfused/pregnant in prior 3 months per AABB */, accession_number UNIQUE). test_results(id PK, sample_id FK, test_code, result, instrument_id, performed_at, performed_by FK, reviewed_by FK, esign_id NULL). Patient blood-group and antibody history rows reference sample_id, giving each safety-critical fact a verifiable provenance chain (who drew it, when, on what instrument) required for audit and dispute resolution.
- **[should-have] Enforce append-only and transition rules at the database layer, with a hardened DB role model** — Create a least-privilege MySQL role for the PHP app with INSERT/SELECT/limited-UPDATE but NO DELETE on audit_logs, patient_blood_groups, patient_antibodies, unit_status_events, electronic_signatures, unit_lineage, recall_items. Put the hash-chain computation and state-machine guards in BEFORE INSERT/UPDATE triggers using SIGNAL SQLSTATE '45000' to reject violations, so enforcement survives application bugs. Provide a separate verifier job (cron) that walks the audit chain and compares the head to the externally anchored head. Document that the DBA/root account is explicitly OUT of the trust boundary for append-only guarantees and is mitigated only by external anchoring — do not claim MySQL triggers alone stop a root user.

- NEW electronic_signatures(signer_user_id FK, signed_at_utc, meaning ENUM, auth_method, reauth_at, signed_payload_hash, audit_log_id FK) — Part 11 §11.50/§11.70/§11.200 signature binding; referenced by quarantine release, QC, crossmatch release, issue, recall.
- NEW recalls(trigger, trigger_donor_id/trigger_donation_id FK, marker, status) and recall_items(recall_id FK, blood_unit_id FK, role, disposition, recipient_patient_id FK patients) — look-back/recall workflow + recipient notification.
- NEW crossmatches(patient_id FK, blood_unit_id FK, method ENUM(serologic_ahg/immediate_spin/electronic), result, performed_by/verified_by FK) — referenced by issue.
- ALTER issue_transactions ADD patient_id FK patients, crossmatch_id FK, issue_esign_id FK, abo_check_passed BOOL — binds issue to recipient identity, compatibility proof, and signature.
- NEW samples(patient_id NULL FK, donor_id NULL FK, collected_by FK, sample_type, expiry, accession_number UNIQUE) and test_results(sample_id FK, test_code, result, esign_id FK) — provenance for all typings/screens.
- DB ROLE change: app role has no DELETE and limited UPDATE on append-only tables; DBA/root explicitly outside trust boundary, mitigated by external hash anchoring.

## PHP/MySQL feasibility
Vanilla PHP/MySQL/AJAX can fully express the RELATIONAL parts of this lane: the patient registry, longitudinal blood-group and antibody history (append-only via INSERT-only code paths + revoked UPDATE/DELETE), the donation->processing_event->component DAG (lineage edge table + recursive CTEs, available in MySQL 8.0+), the unit state machine (transition lookup + BEFORE UPDATE triggers using SIGNAL SQLSTATE '45000' to hard-block illegal transitions like quarantined->issued or issuing an expired unit), and the recall/look-back workflow (recursive CTE over lineage + join to issue_transactions for recipient notification). These are correct and implementable on the stated stack and MUST be enforced in DB triggers, not only PHP, so application bugs cannot bypass safety guards. WHERE THE STACK IS INADEQUATE AT THE SELLABLE BAR: (1) True immutability/tamper-PROOF audit is impossible with MySQL alone — hash-chaining makes tampering DETECTABLE, but a DBA/root user can drop triggers, ALTER tables, and recompute the entire chain. Closing this requires controls OUTSIDE MySQL: append-only/WORM storage for the audit stream, periodic signing and external anchoring of the chain head to a system the DBA does not control, and ideally a separate audit microservice with its own credentials. Recommend a dedicated audit-writer service or at minimum a cron verifier + off-box anchored head. (2) 21 CFR Part 11 electronic signatures require cryptographic binding (signed_payload_hash) and re-authentication at signing (§11.200) — implementable in PHP, but key management, MFA, and signing-key custody are NOT a MySQL concern and need a real secrets/KMS solution; storing signing keys in PHP source or the same DB defeats the purpose. (3) MySQL DATETIME has no built-in trusted time; Part 11/haemovigilance need reliable, ideally NTP-synced UTC timestamps and protection against backdating — the app must capture occurred_at_utc server-side and the anchoring process timestamps it externally. (4) ISBT 128 compliance needs the ICCBBA controlled reference tables and facility registration, not just CHAR columns. (5) Concurrency: reservation/crossmatch/issue races on a single unit need SELECT ... FOR UPDATE row locking (InnoDB) to prevent double-issue; AJAX optimistic UIs make this essential and it must be designed in, not assumed. Net: the schema and guards are feasible and should be built DB-enforced; the audit immutability and Part 11 signature/key/time guarantees require components beyond vanilla PHP/MySQL and must be stated to the buyer as such rather than designed around.

## Risks & tradeoffs
- Tamper-evidence vs. DBA power: hash-chaining detects tampering but cannot PREVENT a root/DBA user from rewriting the whole chain. True immutability requires append-only/WORM storage and periodic external anchoring of the chain head (separate system the DBA does not control). MySQL triggers and privilege revocation are bypassable by anyone who can ALTER tables, drop triggers, or use SUPER/root. Do not oversell MySQL-only as tamper-PROOF; it is tamper-EVIDENT only with external anchoring.
- Evanescent antibodies: alloantibodies can become undetectable over time yet remain clinically significant. A system that selects units only on the current screen WILL cause a delayed hemolytic transfusion reaction. The persistent patient_antibodies history is the mitigation, but it depends on reliable patient identity matching — a patient-identity false-negative (failed MPI match) silently reintroduces the risk. Identity matching is the single highest-risk dependency.
- Patient merges/splits: real MPIs require merging duplicate patients and occasionally un-merging. Merges must carry forward ALL antibody/group history and must themselves be audited and signed; a careless merge can attach the wrong antibody history to a patient (also a safety event). merged_into_patient_id + audit is necessary but merge logic is error-prone.
- ISBT 128 licensing/registration: using ISBT 128 DINs/product codes properly requires an ICCBBA facility registration and the controlled product-code/database; a sold system must either integrate the ICCBBA reference tables or support an alternate identifier scheme per region (e.g. Codabar legacy, Eurocode). Hard-coding will not be standards-compliant.
- Pooled and irradiated/aliquoted products complicate lineage: a pool has many parents (multi-donor look-back) and aliquots share a parent's test status; the DAG handles this but recall queries must traverse BOTH directions (ancestors for donor-positive look-back, descendants for unit-positive recall) and must include co-components from the same donation.
- Performance vs. authority of event logs: making unit_status_events/patient_blood_groups the authoritative source means most queries hit denormalized current-state columns; these must be kept consistent with the event log via the same trigger that writes the event, or drift produces unsafe decisions from stale denormalized state.
- 21 CFR Part 11 is more than a signature table: it also mandates validation of the system (IQ/OQ/PQ), access controls, operational/device checks, and training records. The data model enables compliance but compliance is a process+validation burden the buyer must complete; the schema alone is not 'Part 11 compliant'.
- Append-only growth: hash-chained audit and event tables grow unbounded and cannot be pruned without breaking chains/traceability; need partitioning/archival strategy that preserves chain verifiability across archive boundaries.
