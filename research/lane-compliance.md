# Lane: LANE 2 — Standards-Based, Configurable Compliance

## Executive summary
A sellable region-agnostic blood-bank system must separate UNIVERSAL invariants (full vein-to-vein traceability, irreversible audit trail, segregation/quarantine of untested or non-conforming units, reactive-result lockout, role-based authority checks, electronic-signature accountability, ABO/RhD safety logic) from JURISDICTION-PARAMETERS (deferral periods, donation intervals, age/weight limits, mandatory infectious-disease test panel, record-retention durations, labeling regime, look-back/haemovigilance reporting timelines). The common denominator across WHO Blood Safety guidance, AABB Standards for Blood Banks and Transfusion Services, EU Directive 2002/98/EC + 2004/33/EC + 2005/61/EC + 2005/62/EC, and FDA blood-establishment computer software (BECS) expectations is: every donation, component, test result, and disposition must be reconstructable from donor to recipient and back, indefinitely linkable, and protected by validated software. The compliance layer MUST be data-driven: rules, panels, periods, and labels are configuration rows scoped to a deployment/jurisdiction, evaluated by a generic rule engine, NOT hardcoded PHP. 21 CFR Part 11 (closed-system controls 11.10, signature manifestation 11.50, record/signature linking 11.70, signature components 11.100/11.200/11.300) plus the BECS expectation that the vendor's software is validated in the USER's facility (IQ/OQ/PQ + change control) is the hardest bar; vanilla PHP/MySQL/AJAX CAN meet the functional controls but CANNOT by itself satisfy validation, secure-timestamp, and tamper-evidence guarantees without disciplined added engineering (append-only hash-chained audit, server-authoritative time, locked-down config-change control). ## Recommendations
- **[must-have] Build a generic, data-driven compliance rule engine — never hardcode eligibility/deferral logic** — Donor eligibility, deferral, donation-interval, age/weight, and test-panel rules MUST be stored as evaluable configuration rows, not PHP if/else. Model: a `compliance_ruleset` (versioned, scoped to jurisdiction+deployment+effective-date range) containing `compliance_rule` rows of typed kinds: AGE_MIN/AGE_MAX, WEIGHT_MIN, DONATION_INTERVAL (by component: whole-blood, plateletpheresis, plasmapheresis, double-red), DEFERRAL (temporary with duration, or permanent), HB/HCT_MIN (sex-specific), BP/PULSE ranges, REQUIRED_TEST_PANEL. Each rule carries: operator (>=, <=, between, in-set), threshold value(s), unit, applies-to predicate (sex, component, donor-type), and a human-readable citation field. A single PHP evaluator walks the active ruleset against a donation context and returns pass/defer(until-date)/reject + the triggering rule id. This is the core of region-agnosticism: selling into a new country = loading a new ruleset row-set, zero code change.
- **[must-have] Treat the mandatory infectious-disease test panel as configurable data with mandatory-minimum enforcement** — Universal minimum panel per WHO and EU 2002/98/EC Annex / 2004/33/EC: HIV (1/2), Hepatitis B (HBsAg), Hepatitis C (anti-HCV), and Syphilis. Jurisdiction add-ons (configurable): HTLV-I/II (EU for first-time donors in some states), HBV/HCV/HIV NAT, anti-HBc, Chagas (T. cruzi, AABB risk-based), malaria, West Nile/Zika (FDA seasonal/risk-based), CMV/sickle for special inventory. Model each as a `test_definition` row with: assay name, target marker, result-interpretation map (reactive/non-reactive/indeterminate→released/quarantined/discarded), repeat-reactive algorithm, and a `mandatory` flag per ruleset. A unit MUST NOT be releasable until every test flagged mandatory-in-this-ruleset has a non-reactive (or jurisdiction-defined acceptable) result. Reactive on any mandatory test = automatic, non-overridable quarantine + donor-deferral + look-back trigger.
- **[must-have] Enforce vein-to-vein traceability as a UNIVERSAL non-configurable invariant** — EU 2002/98/EC Art. 14 (traceability) + Directive 2005/61/EC require the ability to trace each unit from donor to recipient and vice versa; the system must guarantee 100% traceability. AABB and WHO require the same. Concretely: an immutable chain donor→donation→component(s)→test_results→disposition(issue/transfer/discard)→recipient/patient, each link carrying who/when/device/lot. The ONLY configurable part is the RETENTION DURATION of these records (see retention rule below), not whether the chain exists. Implement as foreign-keyed, append-only event records; never allow a hard delete of any link.
- **[must-have] Make record-retention periods a configurable parameter with a safe global maximum default** — EU 2002/98/EC Art. 14 / 2005/61/EC require traceability data retained at least 30 years. AABB/US (21 CFR 606.160(d)) requires many records 10 years, some indefinitely. WHO recommends long retention. Model retention as `retention_policy` rows keyed by record-class (donor record, donation, test result, traceability link, audit log, adverse-event report) with a duration per jurisdiction and an enforcement mode (block-purge vs. archive). DEFAULT to the strictest (30y / indefinite for traceability) so an unconfigured deployment is never under-compliant. Retention enforcement must prevent deletion before the period elapses — purge jobs must consult this table.
- **[must-have] Implement 21 CFR Part 11 closed-system controls explicitly (11.10) — this is the validation backbone** — 11.10(a) system validation (see IQ/OQ/PQ rec); (b) ability to generate accurate, complete human-readable AND electronic copies of records for inspection; (c) protection of records over retention period; (d) limiting system access to authorized individuals; (e) secure, computer-generated, time-stamped audit trails recording operator entries/changes WITHOUT obscuring prior values, retained as long as the record; (f) operational system checks enforcing sequencing of steps/events; (g) authority checks (only authorized users perform signings/actions); (h) device checks where relevant; (i) personnel training/qualification controls; (j) written accountability policies for signature misuse; (k) controls over documentation. Map each (a)-(k) to a concrete subsystem and keep a traceability matrix. The audit trail (e) is the single most load-bearing control and must be append-only + tamper-evident.
- **[must-have] Make the audit trail append-only AND tamper-evident (hash-chained) with server-authoritative time** — 21 CFR 11.10(e) demands secure, computer-generated, time-stamped audit trails that do NOT obscure previously recorded information and are retained for the record's lifetime. Vanilla MySQL audit_logs are insufficient because a DBA/app can UPDATE/DELETE rows silently. Required: (1) audit rows are INSERT-only; revoke UPDATE/DELETE at the DB-grant level for the application account on the audit table; (2) each row stores prev_hash + row_hash (SHA-256 over canonical content + prev_hash) forming a chain so any back-dating/deletion breaks verification; (3) timestamps come from the DB server (UTC), never the client/AJAX caller, to defeat clock spoofing; (4) periodic chain-verification job. This is added engineering the base stack does not give you for free — call it out in the SOW.
- **[must-have] Implement electronic signatures per 11.50 / 11.70 / 11.100 / 11.200 / 11.300** — 11.50: each signed record must display the signer's printed name, date/time of signing, and the MEANING of the signature (e.g., reviewed, approved, released, verified) — store these and render them on every report/printout. 11.70: signature is linked to its record so it cannot be cut/copied/transferred to falsify another record (enforce by binding signature to the record's content hash). 11.100: each e-signature is unique to one individual, never reused/reassigned; identity verified before issuance. 11.200: non-biometric signatures use at least two components (user ID + password); first signing in a session requires both components, subsequent continuous-session signings require at least one; signings by others require all components. 11.300: controls over IDs/passwords — uniqueness, periodic checks/revisions/expiry, loss-management/de-authorization procedures, transaction safeguards. Critical release steps (unit release after testing, crossmatch sign-off, issue to patient) MUST capture a meaning-bearing e-signature, not just a session.
- **[must-have] Configurable labeling regime with ISBT 128 as the default standard** — ISBT 128 (ICCBBA) is the international standard for blood/cell/tissue identification: Donation Identification Number (DIN) with check digit, Product Code, ABO/RhD, expiration date, all in linear+Data Matrix barcodes with defined data structures. EU and AABB both move toward/accept ISBT 128; some legacy US sites use Codabar. Model labeling as a `labeling_profile` per deployment: standard (ISBT128 | CODABAR | custom), barcode symbologies, DIN format, product-code dictionary, required label zones, and whether eye-readable + machine-readable both mandatory. Do NOT hardcode label layout. ISBT 128 DIN generation/parsing (incl. check character) and Product Code mapping should be a dedicated module. Flag: true ISBT 128 conformance requires an ICCBBA facility registration number and licensed databases — vendor cannot self-issue.
- **[must-have] Software validation 'in the user's facility' = vendor-provided IQ/OQ/PQ package + change control, not just internal QA** — FDA blood-establishment computer software guidance and the General Principles of Software Validation make the USER (hospital/blood establishment) responsible for validating the software in THEIR environment. As a vendor you must ship a validation package enabling that: (1) IQ — Installation Qualification: documented evidence the software is installed correctly (versions, DB schema version, environment, dependencies, config baseline); (2) OQ — Operational Qualification: scripted test cases proving each function works to spec across boundary/limit/negative cases (e.g., expired unit cannot be issued, reactive unit cannot be released, ABO-incompatible issue is blocked); (3) PQ — Performance Qualification: the facility runs its own real workflows/data and confirms fitness for use. PLUS: a versioned Requirements Spec + traceability matrix (requirement→test), a Validation Master Plan, and formal CHANGE CONTROL (every code/config change is risk-assessed, tested, version-bumped, re-validated as needed, and logged). Without this package the product is not sellable to a regulated blood establishment regardless of code quality.
- **[should-have] Version and scope every compliance configuration; never edit config in place** — Because a unit released yesterday must be judged against the rules in force yesterday, compliance config MUST be temporally versioned. Each ruleset/test-panel/retention/labeling profile carries effective_from/effective_to and is immutable once activated; changes create a NEW version. Disposition records store the ruleset_version_id used so historical decisions are reconstructable and defensible to an auditor. Config changes themselves are signed (11.50) and audit-trailed (11.10e) and run through change control. This closes the loop between Part 11 change control and the data-driven rule engine.
- **[should-have] Designate Responsible Person + role/competency model in data** — EU 2002/98/EC Art. 9 requires a designated 'responsible person' for each blood establishment; AABB requires a qualified medical/technical director and defined personnel competencies. Model roles, qualifications, training records, and per-action authority as data (authority-check source for 11.10(g)). Certain actions (final unit release, deviation approval, recall authorization) are restricted to roles flagged with the requisite qualification, and the responsible-person identity per branch is a configured, auditable field.
- **[should-have] Configurable haemovigilance / serious adverse event & reaction (SAE/SAR) and look-back reporting** — EU Directive 2005/61/EC mandates notification of serious adverse events and reactions; AABB and WHO require haemovigilance and look-back. Reporting CONTENT (severity grading, imputability scale, data fields) is largely common, but RECIPIENTS, TIMELINES, and FORMATS are jurisdiction-specific. Model an `adverse_event` subsystem with configurable report templates and submission deadlines per jurisdiction, plus an automatic look-back trigger when a donor later tests reactive (find all prior components/recipients via the traceability chain). Export should target HL7 v2 / FHIR AdverseEvent + BiologicallyDerivedProduct resources for interoperability rather than a proprietary format.
- **[should-have] Use HL7 v2 / FHIR as the interoperability boundary, not a custom API** — To be sellable into real hospitals the system must exchange with HIS/LIS. Universal expectation: inbound test results (HL7 v2 ORU / FHIR Observation, DiagnosticReport), blood orders (OML/ORM / FHIR ServiceRequest), patient/encounter context (ADT / FHIR Patient, Encounter), and product representation (FHIR BiologicallyDerivedProduct, SupplyDelivery). Treat this mapping as a configurable interface profile per site. Vanilla PHP can produce/parse these but needs a real HL7/FHIR library, not string concatenation; call out the integration-engine gap.
- **[should-have] Classify each compliance parameter explicitly as UNIVERSAL or CONFIGURABLE in the design doc** — UNIVERSAL (hardcoded invariants, safety-critical): existence of full traceability; quarantine-until-tested; reactive-result lockout from release; ABO/RhD compatibility enforcement on issue; no-issue-past-expiry; append-only audit; authority checks; unique non-reusable signatures; segregation of conforming vs non-conforming inventory. CONFIGURABLE (per-jurisdiction data): deferral periods & reasons, donation intervals per component, donor age/weight/Hb thresholds (sex-specific), mandatory test panel composition, record-retention durations per record-class, labeling standard/format, SAE/SAR report templates & deadlines, look-back depth, units of measure & locale, signature-component policy (password vs biometric), required consents. Shipping this explicit table is itself a compliance deliverable auditors will ask for.
- **[nice-to-have] Provide audit-export and human-readable record reproduction for inspectors (11.10(b))** — Inspectors must obtain accurate, complete copies in both human-readable and electronic form. Build a one-click, signature-and-meaning-bearing export per donor/donation/unit/recipient producing a PDF (human-readable) + structured file (CSV/JSON/HL7), including the full audit trail for that object and the ruleset version applied. This is a hard Part-11 acceptance gate and is easy to forget until an inspection fails.

## Data model changes
- compliance_jurisdiction (id, name, country/region code, default_locale, default_uom_system) — top-level deployment scope a hospital is bound to.
- compliance_ruleset (id, jurisdiction_id, version, effective_from, effective_to, status[draft/active/retired], approved_by_user_id, approval_signature_id) — versioned, immutable-once-active container; ties to existing compatibility_rules as one rule-kind among many.
- compliance_rule (id, ruleset_id, rule_kind[AGE_MIN|AGE_MAX|WEIGHT_MIN|HB_MIN|BP_RANGE|PULSE_RANGE|DONATION_INTERVAL|DEFERRAL|REQUIRED_TEST|CONSENT_REQUIRED], operator, threshold_value, threshold_value2, unit, applies_to_json[sex/component/donor_type predicate], defer_duration_days, defer_permanent_flag, citation_text) — replaces hardcoded eligibility logic.
- test_definition (id, ruleset_id, assay_name, target_marker, methodology, mandatory_flag, repeat_reactive_algorithm, result_interpretation_json[result→disposition map]) — drives the configurable mandatory infectious-disease panel; links to existing donation+screening tables.
- donation_test_result (id, donation_id, test_definition_id, raw_result, interpretation[reactive/non_reactive/indeterminate], performed_by_user_id, performed_at_utc, instrument_id, signature_id) — extends screening; gates blood_units.releasable.
- retention_policy (id, jurisdiction_id, record_class, retention_years, indefinite_flag, enforcement_mode[block_purge/archive]) — parameterizes retention; consulted by any purge/archive job.
- labeling_profile (id, jurisdiction_id, standard[ISBT128/CODABAR/CUSTOM], din_format, symbologies_json, product_code_dictionary_ref, required_zones_json, iccbba_facility_number) — drives label generation; new product_code lookup table for ISBT128 Product Codes.
- audit_event (EXTEND existing audit_logs → make append-only): add prev_hash, row_hash (SHA-256 chain), server_time_utc, actor_user_id, action_meaning, target_object_type, target_object_id, before_value_json, after_value_json, ruleset_version_id; revoke UPDATE/DELETE grants at DB level.
- electronic_signature (id, signer_user_id, signed_at_utc, signature_meaning[reviewed/approved/released/verified/recalled], target_object_type, target_object_id, target_content_hash, signing_components_used[id_only/id_pw/full]) — implements 11.50/11.70/11.100/11.200.
- user_credential_policy / signature_policy (id, jurisdiction_id, min_components, password_expiry_days, reuse_prohibited_flag, biometric_allowed_flag) — implements 11.300 and configurable signature component policy.
- role / role_authority (role_id, action_code, requires_qualification_flag) and user_qualification (user_id, qualification_type, valid_from, valid_to, training_record_ref) — authority checks (11.10g) + EU responsible-person/competency.
- adverse_event (id, type[SAE/SAR], severity, imputability, linked_unit_id, linked_recipient_id, report_template_id, deadline_at, submitted_at, submission_target) + report_template (jurisdiction_id, fields_json, deadline_days) — configurable haemovigilance.
- disposition_decision (id, blood_unit_id, decision[release/quarantine/discard/issue/transfer], decided_by_user_id, decided_at_utc, ruleset_version_id, signature_id) — records which compliance version governed each action for reconstructability.
- validation_artifact (id, deployment_id, artifact_type[IQ/OQ/PQ/VMP/trace_matrix/change_record], version, file_ref, executed_by, executed_at, result) — stores the per-facility validation package and change-control log.

## PHP/MySQL feasibility
Vanilla PHP + MySQL + HTML/JS/AJAX CAN meet the FUNCTIONAL compliance controls (data-driven rule engine, configurable test panels/deferrals/retention/labeling, role-based authority checks, e-signature capture with meaning, traceability chain via foreign keys, HL7/FHIR export). It CANNOT meet the sellable bar out of the box on four fronts, each requiring deliberate added engineering: (1) TAMPER-EVIDENCE / 11.10(e): MySQL rows are mutable; you must make audit and signature tables INSERT-only by revoking UPDATE/DELETE at the DB-grant level for the app account, add a SHA-256 prev_hash→row_hash chain, and add a periodic chain-verification job — none of which the stack provides natively. (2) TRUSTED TIME: AJAX clients cannot be trusted for timestamps; all compliance timestamps must come from the DB server in UTC, and the offline-sync queue must re-stamp/re-link on reconciliation. (3) E-SIGNATURE BINDING / 11.70: signatures must bind to a content hash of the signed record so they cannot be transplanted — requires hashing discipline, not just a 'signed_by' column. (4) VALIDATION / BECS: no amount of PHP makes the product 'Part 11 compliant' by itself; the vendor must ship an IQ/OQ/PQ validation package, requirements-to-test traceability matrix, Validation Master Plan, and formal change-control process so the customer facility can validate in their environment — this is documentation/process engineering outside the code. Additionally, real HL7/FHIR and true ISBT 128 conformance need licensed libraries/registration (ICCBBA) the bare stack lacks. PLAINLY: the stack is adequate for the application logic but inadequate, unaided, for tamper-evidence, trusted time, signature binding, and the validation/change-control regime — these gaps must be explicitly engineered and budgeted, or the system is not sellable to a regulated blood establishment.

## Risks & tradeoffs
- Vanilla PHP/MySQL gives no native tamper-evidence: the append-only hash-chained audit trail, DB-level revocation of UPDATE/DELETE on audit/signature tables, and server-authoritative UTC time are ADDED engineering. If skipped, 21 CFR 11.10(e) is not met and the product fails a serious Part-11 audit.
- FDA 21 CFR Part 11 / BECS validation is the USER's facility-level obligation — the vendor CANNOT certify the product as '21 CFR Part 11 compliant' in the abstract. The deliverable is a validation PACKAGE (IQ/OQ/PQ, VMP, traceability matrix, change control) enabling the facility to validate. Marketing the software as 'Part 11 certified' is false and a liability.
- True ISBT 128 conformance requires ICCBBA registration (facility number, licensed databases for Product Codes), which the end-customer must obtain; the vendor cannot mint conformant DINs/Product Codes unilaterally. Default labeling must therefore be a configurable profile, and ISBT128 conformance is gated on customer registration.
- The offline-sync queue conflicts with append-only hash-chaining and server-authoritative time: offline-created records cannot be trusted for timestamps or chain position until reconciled. Reconciliation must re-stamp with server time, re-link the hash chain on sync, and must NEVER allow offline-created release/issue of a unit whose mandatory tests were not server-confirmed — otherwise traceability and reactive-lockout invariants break.
- Configurable rule engine adds power but also risk: a misconfigured ruleset could permit an unsafe donation/release. Safety-critical invariants (ABO/RhD compatibility, reactive lockout, expiry, quarantine-until-tested) must be UNIVERSAL hardcoded guards that the config layer cannot override, only tighten.
- Retention defaults must fail safe to the strictest (30y / indefinite for traceability per EU 2002/98/EC). An unconfigured or under-configured deployment must never purge below the global maximum, or it silently becomes non-compliant.
- Temporal versioning of compliance config increases query/schema complexity (every disposition must record the ruleset_version applied). Omitting it makes historical decisions indefensible to auditors, so the complexity is non-negotiable.
- HL7 v2 / FHIR interoperability cannot be done with PHP string concatenation at the sellable bar; a real HL7/FHIR library or integration engine is required, which is outside the assumed stack and must be budgeted.
- Multi-branch + region-agnostic means a single deployment may span jurisdictions with conflicting rules (e.g., different deferral periods). The model must bind each BRANCH/establishment to its own jurisdiction+ruleset, not assume one global config per install.
