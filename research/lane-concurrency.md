# Lane: LANE 5 — Concurrency, Reservation Locking & Multi-Branch Offline Sync

## Executive summary
A sellable multi-branch blood bank must guarantee that any single blood unit (one physical bag, one ISBT 128 DIN) is allocated/issued exactly once, globally, even under concurrent operators and network partitions. Within a single MySQL instance this is fully solvable with pessimistic row locks (SELECT ... FOR UPDATE) plus a state machine on the unit (available -> reserved -> crossmatched -> issued) and timed reservations with auto-release. Real-time multi-branch visibility via 30s AJAX polling is acceptable for awareness but NOT for correctness; correctness must be enforced server-side at the moment of state transition, never by what the polling UI showed. The genuinely hard, partially-unsolvable part is OFFLINE-then-SYNC: if two branches can independently issue the SAME unit while partitioned, NO merge strategy can un-transfuse blood. Last-write-wins is unsafe because it silently discards one of two conflicting issues. The honest minimum viable architecture is: a single authoritative central MySQL (single source of truth for unit ownership and issuance), branches that degrade to READ-ONLY / queue-only when offline, and exclusive ownership of each physical unit assigned to exactly one branch so a partitioned branch can only commit transitions for units it already exclusively owns. Vanilla PHP/MySQL/AJAX CAN meet the bar ONLY with this architecture and added components (a real-time push channel, an idempotent sync API, and a partition-degradation policy). True multi-master offline-write of shared inventory cannot be made safe and should be refused as a feature.

## Standards referenced
- ISBT 128 (ICCBBA) — Donation Identification Number (DIN) as the globally unique physical-unit key enabling double-issue detection and traceability
- AABB Standards for Blood Banks and Transfusion Services — crossmatch/reservation hold workflow, electronic crossmatch, look-back/recall on distribution errors
- FDA 21 CFR Part 11 — electronic records: attributable, time-stamped, immutable, tamper-evident audit trail for every transition and offline replay
- WHO blood safety / traceability guidance — vein-to-vein traceability of each unit
- EU Blood Directive 2002/98/EC and 2005/61/EC — traceability and serious adverse event/reaction (haemovigilance) reporting, supporting the mandatory conflict/look-back workflow
- HL7 / FHIR (BiologicallyDerivedProduct, ServiceRequest, Provenance) — interoperability and provenance for issuance events and audit
- CAP theorem (Brewer) — formal basis for refusing offline multi-master of an exclusive-allocation invariant
- MySQL 8.0 InnoDB Locking Reads documentation — SELECT FOR UPDATE / FOR SHARE / NOWAIT / SKIP LOCKED semantics

## Recommendations
- **[must-have] Enforce single-issuance with pessimistic row locks inside one transaction** — Each blood_unit row carries status ENUM('available','reserved','crossmatched','issued','quarantined','discarded','transferred_out'). Reserve/issue path: SET autocommit=0; START TRANSACTION; SELECT status,version,reserved_until FROM blood_units WHERE din=? FOR UPDATE; assert status='available' (or 'reserved' by same request for issue); UPDATE blood_units SET status='reserved', reserved_by=?, reserved_for_request=?, reserved_until=NOW()+INTERVAL 30 MINUTE, version=version+1 WHERE din=?; INSERT audit row; COMMIT. The FOR UPDATE serializes concurrent operators on that exact row so the second loser sees 'reserved' and is rejected. This is the core correctness guarantee and is non-negotiable.
- **[must-have] Use FOR UPDATE SKIP LOCKED for 'allocate any compatible unit', NOWAIT for targeted actions** — When the operator requests a blood TYPE (not a specific bag), select the best candidate with: SELECT din FROM blood_units WHERE abo_rh=? AND status='available' AND expiry>NOW() ORDER BY expiry ASC LIMIT 1 FOR UPDATE SKIP LOCKED; this lets concurrent operators each grab a different unit without blocking, eliminating contention storms (FEFO allocation = First Expiry First Out). For actions on a specific DIN the operator already named, use FOR UPDATE NOWAIT so the UI fails fast ('unit is being actioned by another user') instead of hanging. Source: MySQL 8.0 InnoDB locking-reads docs confirm SKIP LOCKED removes locked rows from the result and NOWAIT errors immediately.
- **[must-have] Pin isolation level to READ COMMITTED for the OLTP path** — Default REPEATABLE READ adds gap/next-key locks that increase deadlock frequency on range scans of inventory and can lock phantom ranges you do not intend. Set transaction isolation level READ COMMITTED for the reservation/issue connections to reduce gap locking while still being fully safe because correctness comes from the explicit FOR UPDATE row lock, not from snapshot isolation. Keep statement-based replication OFF (use ROW or MIXED) since NOWAIT/SKIP LOCKED are unsafe for statement-based replication.
- **[must-have] Reservation TIMEOUT with auto-release, enforced lazily not by a cron alone** — Store reserved_until timestamp. Do NOT rely solely on a cleanup cron (cron lag = locked-forever units). Instead make every allocation query treat 'reserved AND reserved_until<NOW()' as available: WHERE status='available' OR (status='reserved' AND reserved_until<NOW()). When a request grabs such an expired reservation under FOR UPDATE, it overwrites it and writes an audit 'reservation_expired_reclaimed' row. Add a low-frequency cron as belt-and-suspenders to flip stale rows back and emit alerts. Typical timeout: crossmatch/hold window per AABB workflow (e.g. 30–60 min reserve, longer explicit crossmatch hold). Make the timeout configurable per hospital.
- **[must-have] Always add a deadlock-retry wrapper** — InnoDB WILL pick a deadlock victim (ER_LOCK_DEADLOCK 1213) or hit lock-wait timeout (1205) under concurrency. Wrap the transactional function in a retry loop (e.g. up to 3 attempts with small jitter backoff) that re-runs the whole transaction on 1213/1205. Without this, legitimate concurrent issues randomly fail. This is mandatory, not optional, for any FOR UPDATE design.
- **[must-have] Treat AJAX polling as awareness only; enforce at commit** — 30s polling of an inventory/dashboard endpoint is fine for showing branch stock levels and incoming alerts. NEVER let the client's last-seen state authorize an action. The server re-validates under FOR UPDATE at the instant of the transition. Add an ETag/last_modified or a monotonically increasing inventory_version per branch so polling can return 304/'no change' cheaply and reduce DB load. Poll the change-feed, not the whole table.
- **[should-have] Add a real-time push channel as a separate component, and be explicit it is not 'vanilla PHP'** — For genuine real-time multi-branch visibility, use Server-Sent Events via a dedicated hub: Mercure (Go binary, SSE, JWT-authorized topics — PHP just POSTs updates to the hub), or Centrifugo/Soketi for WebSockets, or a PHP daemon (Swoole/OpenSwoole, Workerman, Ratchet). SSE/Mercure is the lowest-friction choice: one-way server->client is exactly the visibility need, survives proxies better than raw WS, and PHP stays request/response by publishing to the hub after each committed transaction. Document clearly to the buyer that this is an added always-on process with its own deploy/monitoring — the classic LAMP box cannot push by itself. Keep 30s polling as the fallback when the hub is unreachable.
- **[must-have] Single authoritative central DB for unit ownership; branches are not co-equal masters** — Designate one central MySQL as the single source of truth for which branch OWNS each physical unit and for issuance facts. Branches read/write against it when online. This collapses the hard distributed problem into the solved single-instance FOR UPDATE problem for the 99% online case. Use MySQL replication (or Group Replication/InnoDB Cluster) for HA of the central node, NOT for multi-master writes of inventory. Multi-primary write topologies (Galera/Group Replication multi-primary) still conflict-resolve at COMMIT and will roll back one of two concurrent issues with a certification error — they do not give you offline writes and add operational complexity; avoid for this domain.
- **[must-have] Offline mode = exclusive per-unit ownership + restricted writes, never shared-inventory multi-master** — The ONLY safe offline-write model: each physical unit is exclusively owned by exactly one branch at a time (ownership transfer is itself an online, locked, central transaction). A partitioned branch may ONLY reserve/issue units it ALREADY exclusively owns; it may NOT touch units owned by other branches, and inter-branch transfer is impossible while offline (it requires the central authority to move ownership). This makes offline issuance conflict-free by construction: two branches can never issue the same unit because only one owns it. Everything the offline branch does is queued and replayed; because it only acted on units it solely owned, replay never conflicts on issuance.
- **[must-have] Idempotent, append-only event-log sync API; reject last-write-wins for unit state** — Each offline action is recorded as an immutable event with a client-generated UUID (idempotency key), branch_id, unit DIN, prior_version, action, actor, device timestamp AND server-received timestamp. Sync replays events to the central authority which applies them under FOR UPDATE and is idempotent on the UUID (duplicate replay = no-op). LWW is explicitly banned for unit lifecycle because two 'issued' events for the same DIN are a real-world safety incident (two patients, one bag) that LWW would hide by keeping one and dropping the other silently. Instead: detect the conflict (central already has the unit issued/owned elsewhere), DO NOT auto-merge, raise a CRITICAL reconciliation alert, quarantine the unit record, and force human investigation/look-back per AABB. Non-safety-critical fields (e.g. donor phone edits) MAY use LWW or field-level merge.
- **[should-have] Explain why CRDTs do not save you here** — CRDTs (e.g. OR-Sets, counters) give conflict-FREE merge but only for data types whose conflicts are semantically mergeable. 'This physical bag was transfused into exactly one patient' is a UNIQUENESS/exclusive-allocation constraint, which is provably NOT expressible as a CRDT under partition (it is equivalent to distributed mutual exclusion, which CAP forbids under AP). A CRDT would happily merge two issuances into a set of two — arithmetically clean, clinically catastrophic. CRDTs are useful for soft state (presence, last-known stock COUNTS for display, comment threads) but cannot enforce single-issuance. Use them, if at all, only for advisory visibility, never for the issuance invariant.
- **[should-have] Partition-issue containment and look-back procedure** — Accept that the residual risk (a unit issued in two branches) is eliminated by exclusive ownership BUT add defense in depth: (a) at the bedside/issue step require scanning the ISBT 128 DIN + patient ID (electronic crossmatch / positive patient ID) so a double-issue would require the same physical bag in two places, which is physically impossible if ownership is exclusive; (b) on every reconnect, run a reconciliation that flags any DIN with conflicting terminal states and triggers a 21 CFR 11 audit-logged investigation and, if a unit was wrongly distributed, a recall/look-back. Build the alerting and quarantine workflow now, not later.
- **[must-have] 21 CFR Part 11 compliant audit and tamper-evidence on the sync log** — Every state transition and every replayed offline event must produce an immutable, attributable, time-stamped audit record (who/what/when/old->new) — both branch-local device time and authoritative server time, since offline device clocks drift and cannot be trusted for ordering. Use server-received ordering (Lamport-style sequence or central auto-increment) as the canonical order. Make audit rows append-only (no UPDATE/DELETE; consider hash-chaining each row to the previous for tamper-evidence) to satisfy Part 11 electronic-record integrity and AABB traceability.
- **[must-have] Be honest in the sales/architecture doc about what 'offline' means** — Sell 'offline-RESILIENT issuance of locally-owned stock with automatic reconciliation', NOT 'full offline multi-branch operation'. Explicitly state: while a branch is partitioned it cannot see other branches' live stock, cannot pull/transfer units from other branches, and can only issue units it already holds. This is the truthful, safe envelope. Promising more is selling a data-integrity failure to a hospital.

## Data model changes
- blood_units: add version INT (optimistic concurrency token, bumped on every transition); status ENUM('available','reserved','crossmatched','issued','quarantined','discarded','transferred_out','in_transit'); owner_branch_id (exclusive owner of the physical unit); reserved_by_user_id; reserved_for_request_id; reserved_until DATETIME; crossmatch_hold_until DATETIME
- blood_units: add din VARCHAR (ISBT 128 Donation Identification Number) as the global unique physical-bag key used for idempotency and double-issue detection; UNIQUE constraint
- unit_ownership_log: append-only history of which branch exclusively owned each DIN and when (every transfer = a central, locked transition), for traceability and partition reasoning
- reservations: id, din, request_id, branch_id, user_id, created_at, reserved_until, state ENUM('active','consumed','expired','released'); enables timeout auto-release and audit (or fold into blood_units if 1:1)
- sync_events (event log): event_uuid (client-generated, UNIQUE — idempotency key), branch_id, device_id, entity_type, entity_din, action, prior_version, payload JSON, device_ts, server_received_ts, applied_at, apply_result ENUM('applied','duplicate_noop','conflict_quarantined'); append-only
- sync_conflicts: event_uuid, din, conflicting_state, central_state, detected_at, resolution_status ENUM('open','investigating','resolved','recall_initiated'), investigator_user_id — drives the mandatory human reconciliation workflow
- branches: add last_seen_online_at, inventory_version BIGINT (monotonic counter bumped on any local inventory change) to power cheap 304/no-change polling and change-feed pulls
- audit_logs: add prior_version, new_version, server_ts, device_ts, prev_row_hash (hash-chain for tamper-evidence), actor_id, source ENUM('online','offline_replay') to meet 21 CFR Part 11 attributability/integrity
- inventory_change_feed (or reuse audit_logs as feed): branch_id, seq BIGINT auto-increment, din, change_type, created_at — clients poll/SSE since last seq instead of scanning full inventory
- blood_requests: add reservation_state and reserved_unit_dins to tie hospital requests to held units with their timeouts

## PHP/MySQL feasibility
Single-site concurrency: FULLY FEASIBLE on vanilla PHP/MySQL. InnoDB SELECT ... FOR UPDATE gives exclusive row locks; wrap reserve/issue in START TRANSACTION, lock the unit row, assert state, transition, COMMIT. This is the correct, standard pattern and meets the bar. Confirmed from MySQL docs: FOR UPDATE sets exclusive locks blocking other FOR UPDATE/FOR SHARE/writes until commit/rollback; NOWAIT errors immediately instead of blocking (use for snappy UI), SKIP LOCKED skips locked rows (use for queue-style 'grab next available unit of type X'). Autocommit MUST be off and the whole read-check-write must be inside one transaction — a SELECT then a separate UPDATE without FOR UPDATE is the classic double-allocation bug. Optimistic locking (version column / WHERE status='available') is an adequate, lighter alternative for low contention and is the ONLY option that survives the offline/replay case.\n\nReal-time visibility: PARTIALLY FEASIBLE but with a hard caveat. Vanilla PHP is request/response and cannot push. 30s polling means a unit can appear available in branch B's UI for up to 30s after branch A reserved it. That is acceptable ONLY because the authoritative FOR UPDATE check at commit time rejects the stale action. Polling is fine for dashboards; it is NOT a locking mechanism. True push (WebSockets/SSE) is NOT achievable in vanilla PHP alone — it requires an additional long-running process outside the classic LAMP request model (Ratchet/Swoole/Workerman daemon, or a separate Mercure/Centrifugo/Soketi hub, or Node). That is an added moving part the 'vanilla PHP' framing omits.\n\nOffline-then-sync of SHARED inventory: NOT SAFELY FEASIBLE as multi-master, on ANY stack, not just PHP. This is a CAP-theorem wall, not a PHP limitation. If two partitioned branches can both issue the same unit, the system has lost the single-issuance invariant and no sync algorithm recovers it (you cannot un-issue blood). The PHP/MySQL stack does not make this worse or better — the architecture (who is allowed to write what while offline) is what matters. The stack CAN implement the safe version (exclusive per-unit branch ownership + offline writes restricted to owned units + idempotent central reconciliation).\n\nVerdict: vanilla PHP/MySQL/AJAX is sufficient for single-site safety and good-enough visibility, but the 'real-time multi-branch + offline-safe shared inventory' promise as literally stated is partly undeliverable and must be re-scoped, plus it silently requires at least one non-vanilla component (a push daemon or hub) to feel real-time.

## Risks & tradeoffs
- CAP wall: single-issuance is a strong-consistency (CP) invariant; you cannot have it AND full offline availability (AP) of shared inventory under partition. Any design claiming both is wrong. The mitigation (exclusive per-unit ownership) buys safe offline at the cost of forbidding cross-branch operations while partitioned — a real functional limitation that must be disclosed.
- Pessimistic FOR UPDATE under high concurrency risks deadlocks and lock-wait timeouts; mandatory retry logic adds complexity and, if mis-tuned, tail latency. SKIP LOCKED reduces this but returns an inconsistent snapshot so it must only be used for 'pick-any-available' allocation, never for reporting/counts.
- Real-time push requires an always-on non-PHP process (Mercure hub / Swoole / Centrifugo). This breaks the 'vanilla PHP, drop on any LAMP host' selling point and adds deploy, monitoring, and failure-mode surface. If omitted, 'real-time' is really 'up to 30s stale', which must be stated honestly.
- 30s polling at scale (many branches/users) creates steady DB load; without a change-feed/version/ETag mechanism it does full-table reads repeatedly. Needs the inventory_version + since-seq feed to stay cheap.
- Offline device clocks cannot be trusted for ordering; relying on device timestamps for conflict resolution is a latent bug. Must use central server-received ordering as canonical, which means offline actions are only truly ordered upon reconnect.
- Reservation timeout tuning is clinically sensitive: too short auto-releases units mid-crossmatch (clinical disruption); too long strands inventory during shortages. Must be configurable and audited, and the lazy-reclaim-on-read pattern must be correct or units leak.
- Multi-primary MySQL (Galera/Group Replication multi-primary) looks like it gives multi-branch writes but resolves conflicts by rolling back one committer at COMMIT — it provides neither offline operation nor a free pass on the invariant, and adds heavy ops burden; choosing it under the illusion of 'multi-master = offline-safe' is a trap.
- Residual human/process risk: even with exclusive ownership, a manual override or mis-scanned DIN can cause a double-issue. ISBT 128 barcode scanning + positive patient ID at issue is required as the physical backstop; software locks alone are insufficient for the clinical safety bar.
- LWW anywhere near unit lifecycle is a silent data-loss/safety failure; if any developer applies a generic 'newest record wins' merge during sync, the system can hide a two-patient-one-unit event. This must be architecturally forbidden and code-reviewed, not left to convention.
