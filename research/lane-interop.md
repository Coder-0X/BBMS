# Lane: LANE 3 — STANDARDS-BASED LABELING & INTEROPERABILITY

## Executive summary
A sellable multi-hospital blood bank must abandon generic QR codes and adopt ISBT 128 (ICCBBA ST-001) as its native identification and labeling scheme: a globally unique 13-character Donation Identification Number (DIN), structured Product Description Codes, ABO/Rh and special-attribute data structures, and expiry encoded in the ICCBBA-mandated symbologies (linear Code 128 for the base label, Data Matrix ECC200 for the compact 2D/"Eye-readable + machine" label). The system must register for an ICCBBA Facility Identification Number (FIN) per legal entity and license the ISBT 128 database (Product Description Code tables, country codes, etc.), because the codes are externally governed lookup tables that change — they cannot be hand-coded as a static enum. Interoperability is not optional for sale beyond a single silo: hospitals run a HIS/EHR (patient identity, ADT), a LIS (orders/results), and increasingly an FHIR API gateway, and they will require the blood bank to (a) consume ADT/patient demographics, (b) exchange transfusion/compatibility-test orders and results via HL7 v2 OML/ORM and OUL/ORU (with BTS-specific segments BPO, BTX, TCD, and SAC/specimen), and (c) report the actual transfusion act back to the EHR (FHIR BiologicallyDerivedProduct + MedicationAdministration/Procedure, or HL7 v2 transfusion ORU). Vanilla PHP/MySQL/AJAX can host the data and render ISBT 128 labels, but it cannot by itself meet the integration bar: it needs a real HL7 interface engine (MLLP/TCP listener, message queue, ack handling), a FHIR-conformant REST facade, certified ISBT 128 label rendering, and validated check-character/symbology generation — none of which are AJAX-over-HTTP concerns. Say plainly: a single-silo PHP app with QR codes is unsellable to an accredited hospital; the interoperability and labeling layers are a separate, standards-validated subsystem.

## Recommendations
- **[must-have] Adopt ISBT 128 DIN as the primary unit identifier (replace internal/QR IDs)** — Implement the ISBT 128 Donation Identification Number per ICCBBA Data Structure 001. Structure: 13 visible characters = 5-char alphanumeric Facility Identification Number (FIN, ICCBBA-assigned, first char is a country/registration prefix) + 2-digit year + 6-digit serial number, followed by 2 supplementary 'flag' characters (one of which carries the ISO 7064 MOD 37-2 check character computed over the 13 data chars). The barcode data identifier is '=' . Store DIN as a first-class immutable column; never reuse, never let two facilities collide (uniqueness is guaranteed by the FIN, which is WHY a per-branch/per-legal-entity FIN registration with ICCBBA is mandatory). Each branch that independently collects/labels must have its own FIN.
- **[must-have] Register with ICCBBA and license the ISBT 128 reference tables** — Obtain a Facility Identification Number (FIN) and an annual ICCBBA registration per facility, and license the ISBT 128 Database (Product Description Code table ~ thousands of entries, Special Testing codes, Country/Collection codes, container manufacturer codes). These are externally maintained and versioned; the app must load them as reference data and support periodic updates — they CANNOT be a static hardcoded list. Build a 'reference data import' job (CSV/Excel from ICCBBA) feeding lookup tables.
- **[must-have] Implement Product Description Codes (Data Structure 003) instead of free-text component names** — Every component (e.g. RED BLOOD CELLS LEUKOCYTES REDUCED, FRESH FROZEN PLASMA, APHERESIS PLATELETS) must carry an 8-char Product Description Code: 5-char product code + 3 attribute chars (collection type, intended use/division, etc.) per ICCBBA Reference Table. This encodes anticoagulant, additive, leukoreduction, irradiation, CMV-negative, washed, divided/split (E-codes for splits), volume class. Map your internal component catalog onto these codes; the human-readable component name on the label MUST be the ICCBBA-defined text for that code.
- **[must-have] Encode ABO/Rh, expiry, and special attributes in their own ISBT 128 data structures** — Use Data Structure 002 for ABO/RhD blood groups (with the 'biohazard/blood group confirmation' flagging), Data Structure 005 for Expiration Date (and Data Structure 006 when expiration time is needed for short-dated platelets), Data Structure 004 for Collection Date, and Data Structure 022/023 for Special Testing / red cell antigens (e.g. CMV-neg, sickle-neg, antigen phenotype). Expiry must be machine-readable on the label, not just printed.
- **[must-have] Use ICCBBA-mandated symbologies: Code 128 (linear) + Data Matrix ECC200 (2D); drop QR** — ISBT 128 label production specifies linear barcodes in Code 128 symbology with defined Data Identifier prefixes ('=' for DIN, '=<' for product code, '=%' for ABO/Rh, '=>' for expiry per the standard's data identifier scheme), arranged in the canonical four-quadrant label layout (DIN top-left, Product top-right, ABO/Rh bottom-left, Expiry bottom-right). The 2D option is Data Matrix ECC200 (NOT QR), which can concatenate multiple data structures into one symbol for handheld scanning. QR is inadequate because: (1) it is not part of the ISBT 128 standard, so scanners/LIS at accredited sites will not parse it; (2) it has no defined data-identifier/concatenation grammar for blood data structures; (3) it provides no standardized check-character validation tied to the DIN; (4) AABB/regulatory and HIS vendors expect Code 128/Data Matrix; a QR label fails interoperability and likely accreditation. Implement a validated label-rendering module producing exact barcode dimensions, quiet zones, and human-readable interpretation lines.
- **[must-have] Stand up a real HL7 v2 interface engine (MLLP listener), not AJAX endpoints** — Hospitals integrate the blood bank/transfusion service via HL7 v2.x over MLLP (Minimal Lower Layer Protocol) on TCP. You must run a persistent listener that frames messages (VT...FS CR), validates, sends ACK/NAK (MSA), persists, and retries. Support inbound ADT (A01/A04/A08/A40 merge) for patient identity, ORM^O01/OML^O21 for orders (type & screen, crossmatch, issue), and emit ORU^R01/OUL^R22 for results. Blood-bank-specific segments: BPO (Blood Product Order), BTX (Blood Product Transfusion/Disposition), TCD, SAC/SPM (specimen/container), and the dispense in OMB/RDE patterns. PHP CANNOT do this as request/response AJAX; you need a long-running daemon (separate service, e.g. a PHP CLI worker or a dedicated engine like Mirth/NextGen Connect) plus a message queue and dead-letter handling.
- **[must-have] Expose a FHIR R4 REST facade for modern EHR integration** — Implement FHIR resources: Patient + (often) Coverage for identity; ServiceRequest for the transfusion/compatibility order; Specimen for the sample; Observation for blood-group, antibody-screen, crossmatch results (LOINC-coded); BiologicallyDerivedProduct (R4) / BiologicallyDerivedProduct + BiologicallyDerivedProductDispense (R5) for the unit itself; MedicationAdministration or Procedure for the transfusion event reported to the EHR; DiagnosticReport for the transfusion-service report; Provenance for traceability. Support read + search + (where the EHR pushes) create, with a CapabilityStatement. Use US Core / IPS-style profiles where applicable and LOINC/SNOMED/the ISBT 128 code system (FHIR has a defined ISBT 128 NamingSystem/OIDs) for unit identifiers. A FHIR facade is the increasingly mandatory path for selling beyond legacy v2 sites.
- **[must-have] Define explicit integration points for HIS, LIS, and EHR** — (1) PULL patient identity from HIS: subscribe to ADT feed (v2) or query FHIR Patient/$match; never let staff retype MRN/name — vein-to-vein traceability requires the authoritative patient ID. (2) ORDER exchange with LIS: receive type&screen/crossmatch/issue orders (OML^O21 / ServiceRequest), return results (OUL^R22 / Observation+DiagnosticReport); reconcile specimen IDs (SPM/Specimen) to enforce the one-sample/electronic-crossmatch rules. (3) REPORT transfusion to EHR: on issue and on confirmed transfusion, emit BTX disposition / MedicationAdministration so the EHR records the act, the DIN, lot/expiry, volume, reactions, and links to the patient record. Each is a named, versioned interface with its own conformance profile and test harness.
- **[should-have] Build positive patient/unit ID at the bedside (barcode verification, vein-to-vein)** — Scan patient wristband + unit ISBT 128 + crossmatch tag at issue and at administration; the system must verify DIN-to-patient reservation, ABO/Rh compatibility, expiry, and special requirements (irradiated/CMV-neg) electronically before transfusion. This closed-loop step is an AABB/Joint-Commission expectation and a core selling point; it depends entirely on machine-readable ISBT 128, which generic QR cannot satisfy across vendor scanners.
- **[should-have] Map your static compatibility_rules table to standards-coded vocabularies** — Express compatibility, antigen, and special-attribute logic in terms of ISBT 128 codes and LOINC/SNOMED, not internal strings, so results and rules are portable to LIS/EHR. Keep the rule engine but key it on the coded attributes carried in the Product Description Code and ABO/Rh data structures.
- **[should-have] Treat label generation and interface messages as validated, version-pinned artifacts** — Under 21 CFR Part 11 / accreditation, label layouts, barcode encodings, and message mappings are validated configuration. Version every Product Description Code table load, every label template, every HL7/FHIR mapping; keep an audit trail of which version produced each label and each message (ties into your audit_logs). Provide test/print-verification mode and a barcode read-back self-test.
- **[nice-to-have] Provide an interface conformance & onboarding toolkit per hospital** — Ship configurable connection profiles (host/port/MLLP vs FHIR endpoint, message-type filters, segment field maps, character set UTF-8/ISO-8859, ACK mode), plus a simulator and conformance test suite, because every hospital's HIS/LIS dialect differs slightly. Selling to multiple hospitals means each site is an integration project; productize it.

## Data model changes
- blood_units: add isbt128_din CHAR(13) UNIQUE NOT NULL (immutable), din_check_char, din_flag_chars; deprecate/relegate any QR-derived internal id to a non-authoritative surrogate key.
- blood_units: add product_description_code CHAR(8) FK -> ref_product_codes; replace free-text component_name with derived ICCBBA text.
- blood_units: add abo_rh_code (DS-002 encoded) and abo_rh_confirmation flag; add collection_datetime (DS-004) and expiry_datetime (DS-005/006, time-precise for platelets).
- New ref_product_codes table (ICCBBA Product Description Code table: code, description_text, class, attributes) loaded from licensed ISBT 128 database; versioned.
- New ref_country_codes / ref_facility_fin table (FIN registry incl. each branch's ICCBBA-assigned FIN); facilities table gains iccbba_fin column.
- New ref_special_testing table (DS-022/023 antigen & special-attribute codes) + unit_special_attributes link table (irradiated, CMV-neg, washed, antigen-neg, divided/split E-code).
- New label_templates + label_print_log (template version, din, symbology images/checksums, printed_by, printed_at) for Part 11 validation traceability.
- New hl7_messages table (direction, msg_type e.g. ORM/OML/ORU/OUL/ADT/BTX, raw_payload, control_id, ack_status, parsed_refs, ts) plus hl7_endpoints (host, port, mllp/fhir, mappings).
- New fhir_resources / fhir_event_outbox table to stage BiologicallyDerivedProduct, ServiceRequest, Observation, MedicationAdministration, Provenance payloads and delivery status.
- New patient_identity table sourced from HIS ADT/FHIR Patient (authoritative MRN, identifiers list, merge history A40) — distinct from locally typed data; link blood_requests/reservations to it.
- specimens table (SPM/Specimen): specimen_id, patient_identity_id, collected_at, type, for crossmatch/type&screen linkage to orders.
- orders table extended to carry HL7 order control id, BPO blood-product-order fields, and FHIR ServiceRequest id; results carry LOINC codes.
- transfusion_events table (vein-to-vein): din, patient_identity_id, administered_at, administered_by, volume, reaction, source order, EHR report status (BTX/MedicationAdministration ack).
- Reference-data version tables (table_version, effective_date, source) for ICCBBA code releases to satisfy versioned-config audit.

## PHP/MySQL feasibility
Mixed. MySQL is fully adequate to MODEL ISBT 128 (DIN, product/ABO/expiry codes, reference tables, version history) and to store HL7/FHIR payloads. PHP can RENDER ISBT 128 labels if you add a validated barcode library producing Code 128 and Data Matrix ECC200 with correct data identifiers, quiet zones, human-readable lines, and ISO 7064 MOD 37-2 check characters — generic QR libraries are NOT acceptable. Where vanilla PHP+AJAX breaks at the sellable bar: (1) HL7 v2 integration requires a persistent MLLP/TCP daemon with framing, ACK/NAK, queuing, retry, and character-set handling — this is not a web request/response concern; you must run a long-lived worker service or, more realistically, a dedicated interface engine (Mirth/NextGen Connect) alongside the PHP app. (2) A FHIR facade demands conformant REST semantics, CapabilityStatement, search params, and terminology binding — implementable in PHP but only as a deliberately built, version-pinned, conformance-tested subsystem, not ad-hoc AJAX JSON. (3) The ISBT 128 code tables are externally licensed/versioned and cannot be a static enum; the app needs an import/versioning pipeline. (4) Validation (21 CFR Part 11) means label encoders and message mappings are controlled, evidence-backed artifacts. Plainly: a single-silo PHP+MySQL+AJAX app with QR codes cannot be sold to an accredited hospital. The path to sellable is to keep PHP/MySQL as the core domain/inventory app but add three standards-validated subsystems — an ISBT 128 label/identity module, an HL7 v2 interface engine (likely external), and a FHIR REST facade — each independently conformance-tested.

## Risks & tradeoffs
- ISBT 128 is licensed/governed: per-facility ICCBBA registration fees and the requirement to license and periodically update the code tables add recurring cost and an external dependency you cannot fake with a static enum — but it is mandatory for accredited sites and for global uniqueness.
- Generic QR codes are a hard blocker for sale: accredited hospitals, their LIS/HIS, and their handheld scanners expect Code 128 / Data Matrix with ISBT 128 data identifiers; shipping QR makes the product non-interoperable and likely fails accreditation. This invalidates the current 'generic QR' assumption in the plan.
- HL7 v2 over MLLP requires a persistent TCP daemon, message framing, ACK/NAK, queuing, retry, and character-set handling — architecturally outside vanilla request/response PHP+AJAX. Realistically you bolt on an interface engine (e.g. Mirth/NextGen Connect) or a dedicated long-running worker service; the PHP web app becomes one component, not the integration layer.
- FHIR conformance (CapabilityStatement, profiles, terminology binding to LOINC/SNOMED/ISBT 128 NamingSystem) is non-trivial; partial/ad-hoc FHIR will be rejected in EHR vendor certification (e.g. Epic/Cerner connectivity programs).
- Every hospital is a bespoke integration (segment/field-level mapping differences, ADT event subsets, MRN namespaces); selling to many sites means productizing an onboarding/conformance toolkit or carrying high per-site integration services cost.
- 21 CFR Part 11 / EU Blood Directive treat label templates, barcode encoders, and message mappings as validated configuration: changes require versioning, validation evidence, and audit trails, slowing release cadence.
- Check-character (ISO 7064 MOD 37-2) and symbology generation must be validated against ICCBBA test vectors; a subtle encoding bug produces unscannable or mis-identified units — a patient-safety and liability risk, not a cosmetic one.
- Time-precise expiry for platelets (DS-006) and split/divided products (E-codes) add edge cases the inventory/reservation logic must handle correctly to avoid issuing expired or wrong-fraction units.
